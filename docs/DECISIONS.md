# WORLDS — Decision log

## Accepted
- **D-001 Map-first discovery:** location is the product differentiator.
- **D-002 Four launch categories:** Story, Puzzle, Art, Experience.
- **D-003 Open creation:** any authenticated user can create/publish subject to validation, rate limits and moderation.
- **D-004 No AR in MVP:** GPS-based experiences first; prove demand before device-specific complexity.
- **D-005 Supabase/Postgres/PostGIS:** minimize solo-operator burden while supporting spatial queries.
- **D-006 Foreground location only:** privacy, battery and permission simplicity.
- **D-007 Structured blocks:** safe rendering and schema evolution.
- **D-008 Start on the installed Flutter 3.38.3 / Dart 3.10.1:** product-owner decision, 2026-11-19. This SDK is verified on the development machine. Alternatives were a per-project pin to Flutter 3.50.x (latest packages, not verified on this machine) and a global upgrade (changes other projects on the machine). Trade-off: 11 of 17 recommended packages resolve below their latest release. Revisit when a required package needs a newer SDK. Evidence: `docs/REPOSITORY_AUDIT.md`.
- **D-009 Placeholder application ID `com.example.worlds`:** product-owner decision, 2026-11-19. Google Play rejects `com.example`, so a real application ID must replace it before any release build.

The next four were adopted on the audit's recommendation when the product owner said to go ahead with Checkpoint 1 (2026-11-20). The owner did not choose them individually.

- **D-010 Gradle pinned to Java 21 per project:** `android/gradle/gradle-daemon-jvm.properties` contains `toolchainVersion=21`. It overrides the machine's user-level JDK 20 setting for this project only. Alternatives: change the machine-wide setting (could break older projects on the machine) or set `GRADLE_OPTS` in every shell (easy to forget). Requires a JDK 21 on the building machine. Audit decision D2.
- **D-011 Publishable Supabase key:** configuration uses `SUPABASE_PUBLISHABLE_KEY`, because Supabase is deprecating legacy anon and service-role keys by the end of 2026. The app refuses to start with a secret or service-role key. Audit decision D9.
- **D-012 Generated code is committed:** `*.freezed.dart` and `*.g.dart` are committed so a fresh clone builds without running `build_runner`. Audit decision D11.
- **D-013 Hand-written Riverpod providers:** `riverpod_generator`, `riverpod_annotation` and `riverpod_lint` are not used. On Flutter 3.38.3 the generator holds Riverpod at 3.1.0; without it Riverpod resolves to 3.3.2, and the slow `build_runner` step stays limited to Freezed and json_serializable. Revisit if the project moves to a newer Flutter.

Checkpoint 2 decisions:

- **D-014 Usernames chosen at sign-up:** product-owner decision, 2026-11-20. 3–20 characters of lower-case letters, digits and underscores, unique, stored lower-case. If the requested name is invalid or taken when the account is created, sign-up still succeeds with a generated `user_` name the user can change. Alternative rejected: generated names for everyone.
- **D-015 Remote Supabase project as the development database, changed through the MCP connection:** product-owner decision, 2026-11-20. Migrations are dry-run with their tests, applied from the committed file's exact contents, then renamed to the version Supabase records. The MCP connection stays write-capable by the owner's choice; ad-hoc schema changes through it remain forbidden. In Checkpoint 4 the connection asked for approval before data-changing SQL and the editor declined that prompt, so the owner pasted prepared files into the Supabase SQL editor (dry run, apply with its history row, tests). In Checkpoint 5 the connection ran single statements again, so the dry run, the apply and the tests went through it; each prepared file is now one statement that checks its own text against the committed files before running. See `supabase/README.md`.

Checkpoint 3 decisions. The owner said "continue" without choosing, so the first four were adopted on the audit's recommendation (2026-11-20); the rest are implementation choices recorded for review.

- **D-016 Map package `maplibre_gl` 0.27.1:** wrapped behind `MapAdapter` in `lib/core/maps`; a test fails if it is imported anywhere else. Alternative deferred: the newer `maplibre` package (floating native version, much less use). Audit decision D4.
- **D-017 OpenFreeMap tiles for development and pilot:** free, commercial use allowed, no key, no SLA. Stadia Maps Starter ($20/month) remains the pre-approved fallback, switchable through `MAP_STYLE_URL` and `MAP_ATTRIBUTION`. Map tile requests go to this third party, which sees the device's IP address and the areas being viewed. Audit decision D5.
- **D-018 Title search is part of the nearby query:** `get_nearby_worlds` takes an optional `search_text` (case-insensitive, `%` and `_` literal). Resolves audit gap G2.
- **D-019 Browsing needs no account:** the nearby query is callable signed out. Unlocking and playing need an account (D-032).
- **D-020 World text limits (proposed):** title 3–80 characters, trimmed; description at most 2,000 characters. Not specified in the documents; change by a forward migration if the product needs other limits.
- **D-021 Location is read only when the user taps "find Worlds near me":** even if permission was granted earlier. One reading with a 15-second limit; MapLibre's own location layer stays off because it tracks continuously. Before Android's permission prompt, a short dialog explains that location is used only on tap, is not tracked in the background and is never shown to others. Before that, Explore opens at `EXPLORE_DEFAULT_CENTER` if set, otherwise zoomed out. **The pilot area, and so the default centre, is undecided.**

Checkpoint 4 decisions, 2026-11-20. The owner approved Checkpoint 4 and asked for work to proceed without further questions unless genuinely blocked, so these restrictive defaults were taken and reported in the baseline; the owner has not chosen them individually. D-022 is left unused because `docs/USER_JOURNEYS.md` already reserves it for the play-account decision.

- **D-023 Content limits (proposed):** at most 30 parts per World. Text 2,000 characters; caption 200; choice prompt 300, 2–4 options of 80; question 500, hint 300, success message 300, answer 1–100 after normalisation; artwork title 80, description 2,000; ending title 80, message 1,000. Images: JPEG, PNG or WebP, at most 5 MB, at most 40 per World. At most 20 new Worlds per account per day. Enforced by the database; mirrored in `WorldRules` for quick feedback.
- **D-024 Content blocks are readable by their creator only until the player exists:** `docs/DATABASE.md` says blocks are readable whenever the parent World is. That would let anyone read a published World's whole content remotely, including story branches, which defeats the unlock step. Details show only safe fields and a part count. Public content reading is designed with the player in Checkpoint 5.
- **D-025 Which parts each category uses, and how stories branch:** Story uses text, image, choice and ending; Puzzle uses text, image, question and ending; Art uses artwork, text, image and ending; Experience uses all six. A choice may lead only to a later part, so every path moves towards an end and cannot loop. An ending finishes its branch; otherwise the experience finishes after the last part. Publishing needs at least one non-ending part, plus a question (Puzzle), an artwork (Art) or a text part (Story).
- **D-026 Puzzle answers:** one accepted answer per question. It is normalised (Unicode NFKC, lower case, whitespace collapsed, trimmed; accents still count) and stored as a bcrypt hash in `private.world_question_secrets`, which the Data API cannot reach. The creator's app sends it once with a save and only ever learns that an answer exists. Checkpoint 5 must use the same normalisation. Alternatives deferred: several accepted answers per question.
- **D-027 Draft and publish lifecycle:** drafts may be saved before they have a place. "Unpublished" is a draft that has a publish date; the database has no separate status. A published World can be edited, but each save must keep it publishable. Hidden Worlds cannot be edited, published or deleted by their creator. Deleting is a soft delete; files stay in storage until a retention policy exists.
- **D-028 Images:** a private `world-media` bucket with owner-scoped paths and signed addresses. Only the cover of a published public World is readable by others. Photos come from Android's system photo picker, which needs no storage or media permission, are resized to 2,048 px at quality 85, and are checked by their first bytes. `image_picker` alone is used; a separate compression package was not needed. The server checks the stored object's owner, path, declared type and size, but does not decode images. No thumbnails yet (image transforms need a paid plan).
- **D-029 Unlisted Worlds are not offered yet:** gap G1 remains open. The creator cannot choose "unlisted", and details open only published public Worlds (plus the creator's own). Decide with share links in Checkpoint 6.
- **D-030 Backend stays on Supabase Cloud:** product-owner decision, 2026-11-20, after asking to deploy "on AWS". Supabase Cloud already runs on AWS; self-hosting or rebuilding on native AWS services was not chosen. The project's region should be checked against the pilot area before launch.

- **D-031 Visual direction "living atlas / field journal" adopted:** product-owner request, 2026-11-20 ("the UI is not nice … make it high quality"). It implements the direction proposed in `docs/UI_UX_SPECIFICATION.md` section 3 inside Material 3: warm paper canvas `#F7F4EE`, white surfaces, deep botanical green `#1F5E4B`, ochre accent for distance, the existing category colours, Android's system font with a stronger weight and size scale, a 4 dp spacing scale and one radius family (10/14/20/28). Tokens live in `lib/app/theme/app_tokens.dart`; widgets use roles, not hex values. Explore's map now fills the screen with floating search and filters; Worlds without a cover show their category colour with atlas contour lines. Exact values remain open to the owner's review, as are an app icon and launch screen.

- **D-032 An account is needed to unlock and play:** product-owner decision, 2026-11-20 (closes the play part of audit gap G3; `docs/USER_JOURNEYS.md` still calls this decision D-022, a number left unused). Browsing the map and World details stays open to everyone. Tapping Unlock while signed out leads to sign-in and back to the World. Progress, visits and answer attempts belong to the account. Guest play (Supabase anonymous sign-in) was the alternative and can be added later.
- **D-033 Unlock and play rules (proposed):** a World unlocks with one fresh reading of 100 m accuracy or better, within its radius plus up to 25 m of the reading's uncertainty; the position is not stored. Once unlocked it stays unlocked for that account while it is published, so it can be finished anywhere. Unlocked accounts receive all of its parts, without answers and without success messages, which arrive with a correct answer, and may see the images those parts use (not other images uploaded to the World). Each step is checked by the server: the next part, a chosen option's later destination, a question answered first, an ending or the last part finishes; repeated steps change nothing and completion is counted once per finish. Five wrong answers per question in ten minutes pause that question. An unpublished or hidden World cannot be opened or advanced. Starting again keeps the completion count. GPS remains a convenience gate, not proof of presence.

Checkpoint 6 decisions, 2026-11-21. The owner said "pushed continue further" after the Checkpoint 5 report, with the device checks of Checkpoints 4 and 5 still open. These restrictive defaults were taken where the documents leave a choice and are open to the owner's review; none was chosen by the owner individually.

- **D-034 Saved Worlds (proposed):** saving needs an account and a World that is published and public at that moment; removing always works. The list is private to its account: no one else, the creator included, can see who saved a World. At most 500 saved Worlds per account. A saved World that is later unpublished, hidden or deleted leaves the list without being named, is counted as "not available at the moment", and comes back if it is published again. Distances in the list are measured from the location the user last shared on Explore; opening Saved never reads the location.
- **D-035 Reports (proposed):** reporting needs an account. Six reasons: unsafe or private place, harassment or hate, sexual content, dangerous challenge, spam or misleading, something else. Details are optional, at most 500 characters. One pending report per account and World (a second changes nothing and says so), ten reports per account per day, and no reports of one's own World. Only published public Worlds can be reported. A reporter can read their own reports but not their status; creators and everyone else can read none. A report outlives its reporter's account, without the name.
- **D-036 Moderation is done in the dashboard, not in the app (proposed):** there is no moderator role in the app and no moderation API. The project owner, who already controls the database, runs `private.hide_world`, `restore_world`, `remove_world`, `dismiss_reports` and `moderation_queue` in the Supabase SQL editor (runbook in `supabase/README.md`). Each action must name who acted and why and is written to `private.moderation_actions`, which outlives the World. A hidden World is closed to everyone but its creator, who sees its state and cannot edit, publish or delete it. Restoring puts a World back as published only if it was published when hidden and is still complete; otherwise it becomes a draft. Alternative deferred: an in-app moderator role with its own screens, which needs a trusted way to grant the role and widens what an attacker could reach.
- **D-037 Profile pages and counts (proposed):** a profile page shows the public fields and the published Worlds of that account to everyone, signed in or not. The number of published Worlds is public. Discovered (Worlds unlocked) and completed counts, and the count of unpublished Worlds, are shown to the owner only: they describe where a person has been. Every number is counted by the server from real rows (`world_progress`, `worlds`); nothing is estimated.
- **D-038 No share links or unlisted Worlds yet (proposed):** details have no Share action. A link needs a web domain, Android app links and the final application ID, none of which exist, and a button that produced a dead link would be a fake. Gap G1 (unlisted Worlds by direct link) stays open with it. World details and creator pages already have full-page routes (`/worlds/<id>`, `/creators/<username>`) that links could later open.

Checkpoint 7 decisions, 2026-11-21. The owner wrote "pushed continue further" after the Checkpoint 6 report, having pushed that branch, and merged it into `main` later the same day (pull request #8). The moderation and privacy review that report asked for, and D-034 to D-038, were not answered one by one; those words are the only approval on record. Restrictive defaults were taken again and are open to the owner's review.

- **D-039 Product events for the pilot (proposed):** the app sends four events, the only steps of the funnel the server cannot see for itself: Explore opened, a World selected on the map, World details opened, an unlock attempted (with how it ended: unlocked, too far, inaccurate, no location, failed). An event holds a random id made when the app starts, a name and a time. The id lives in memory only and is new at every launch. An event holds no account, no World and no position; no device or advertising id is read. Which Worlds were opened or attempted is kept only as a daily total per World, with no id of any person or launch, so the events do not say where anyone went. The account is not stored with an event, but it can be worked out for a launch that unlocked a World: the `unlocked` event and that account's progress row are written within a second of each other, and in a small pilot that is enough to tell which account a launch belonged to, and so when that launch opened Explore and details. It shows no World and no place beyond what the progress row already holds. Starts, completions, publishing, saving, reporting, creators and repeat creators are counted from their own tables. Everything is read only in the Supabase SQL editor (`private.pilot_funnel`, `pilot_summary`, `pilot_worlds`); the tables are not part of the API. Limits: 200 events per launch and 20,000 in all per 24 hours, beyond which events are dropped; events older than 90 days are deleted when a new launch first reports. A creator opening their own World is not counted. No analytics or crash-reporting SDK was added. Rejected: a third-party SDK (device identifiers, data leaving the project) and keying events to the account (a record of where a person went). Known weakness: the function must be callable signed out, so anyone holding the app's public key can send events; a flood can use up a day's allowance or inflate that day's numbers. The pilot's numbers are indications, not accounts. Testers have not been told about this in any notice yet.
- **D-040 Motion (owner request, 2026-11-21):** during Checkpoint 7 the owner wrote "use good animation and transition and smothness". It was taken as approval to implement the Motion list in `docs/UI_UX_SPECIFICATION.md` section 3, and of nothing else in that section: no colour, shape or type changed. What moves: the preview card rises into place over the map; Explore messages fade and the space they take eases; in the player the next part comes in from the right as the last leaves to the left, the progress bar grows, and a correct answer, a finished World, a World going live and a sent report are each marked once; screens fade from loading into their content; on a locked World the panel's colour, icon and length ease between answers. Durations are 150, 260 and 420 ms and come from one place (`Motion` in `lib/app/theme/app_tokens.dart`), which returns none when the device is set to remove animations. That covers the app's own animations; Flutter's page transitions, ripples, sheets and dialogs are the framework's and still play. Deliberately not animated: the map itself and anything around it (switching tabs, the map and list views, the editor's steps, one of which holds a map), because moving a native map view is where stutter comes from; page transitions, which stay Android's own and keep the predictive back gesture; and nothing loops. Emphasis on the selected map marker is drawn by the native map and was left as it is.
- **D-041 Contrast (measured 2026-11-21; values are the owner's to choose):** every token pair was measured against WCAG 2.1 AA. Fixed without changing a token: in the dark theme category names and icons were drawn in colours chosen for light surfaces (Story 2.3:1, Art 2.8:1, Experience 3.1:1, Puzzle 3.9:1 on a dark card); they now use the lightened shade the category badge already used (6.0:1 or better). Left for the owner, with a proposed value each: Puzzle's amber `#B26A00` as small text on light surfaces is 4.2:1 on white and 3.9:1 on the canvas, short of 4.5:1 (`#8E5500` for text gives 6.1:1 and 5.6:1; icons and markers can keep the amber, which passes the 3:1 they need); the ochre distance label on its own tint over the canvas is 4.2:1 (`#885010` gives 5.1:1); the `outline` token is 1.3:1 to 1.6:1 against surfaces in both themes, which is fine for a quiet separator and is not relied on for field or button edges (those use `muted`, 5.7:1), but it is the only edge of an unselected category card and of the track behind the progress bars.
- **D-041, the owner's answer (2026-11-21):** asked directly, the owner chose "Apply both". In the light theme Puzzle's name is now drawn in `#8E5500` (6.1:1 on white) and the distance label in `#885010` on its tint (5.1:1), the second as a new token, `accentText`; the ochre `accent` and its tints are unchanged. Icons, badges, markers and panels keep their colours. The dark-theme change made earlier was in the same report and drew no objection; it was not asked about separately. Still short in the light theme, measured by hand while applying these and not yet put to the owner: the "Published" label (green on its tint, 4.2:1), the "Unpublished" label (ochre on its tint, 4.1:1 on the canvas), the small note inside the amber "not there yet" panel on the canvas (4.47:1), and the `outline` edge above. The automated walks did not flag any of the four.
- **D-042 Free plan for now (owner decision, 2026-11-21):** asked directly what the pilot should run on, the owner chose to stay on Supabase's Free plan for now. Accepted with it: no backups, so a mistake in the SQL editor or a lost project cannot be undone; and the project pauses after about a week with little activity until someone restores it in the dashboard. Who watches the project, restores it and moderates is still unnamed.
